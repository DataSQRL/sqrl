# PostgreSQL Engine Configuration

PostgreSQL is a realtime database that stores the materialized views and tables generated by your DataSQRL pipeline for low-latency querying.

## Configuration Options

No mandatory configuration keys are required. Physical DDL (tables, indexes, views) is produced automatically by the DataSQRL compiler.

| Key                     | Type        | Default | Description                                                                                                    |
|-------------------------|-------------|---------|----------------------------------------------------------------------------------------------------------------|
| `partition-ttl-divisor` | **integer** | `100`   | Controls the number of partitions for range-partitioned tables with a TTL (see [Partitioning](#partitioning)). |
| `partition-premake`     | **integer** | `4`     | Number of future partitions pg_partman pre-creates ahead of the current one (`p_premake`).                     |
| `index-selection`       | **object**  |         | Limits of the automatic index selection (see [Index Selection](#index-selection)).                             |

## Basic Configuration

```json
{
  "engines": {
    "postgres": {
      "partition-ttl-divisor": 100,
      "partition-premake": 4
    }
  }
}
```

## Partitioning

Tables annotated with `partition_key` on a timestamp column and a `ttl` hint are range-partitioned with pg_partman, and expired partitions are dropped automatically. The partition width is derived from the TTL:

- The TTL duration divided by `partition-ttl-divisor` caps the number of partitions.
- The unit the TTL is declared with sets the minimum width: `ttl(14 days)` never produces partitions smaller than 1 day, while `ttl(336 hours)` allows hourly partitions.
- The result is snapped down to the closest calendar-aligned width from: 15 min, 30 min, 1, 2, 4, 6, 8, 12 hours, 1, 2, 4 days, 1, 2, 4, 8, 12 weeks.

For example, `ttl(14 days)` with the default divisor produces 1-day partitions.

At setup time, pg_partman pre-creates the historical partitions covering the full TTL window (via `p_start_partition`), so replayed or late-arriving data within the retention period lands in a dated partition rather than the DEFAULT partition. The `partition-premake` key controls how many future partitions are created ahead of the current one.

## Index Selection

The compiler selects the indexes of each table from the filters of the API queries that read it (see [Automatic index selection](../sqrl-language#automatic-index-selection)). The `index-selection` object sets its limits:

| Key                     | Type        | Default | Description                                                                                                                                                         |
|-------------------------|-------------|---------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `max-indexes`           | **integer** | `8`     | The most indexes that the compiler selects by query cost for one table. See [When a table needs more indexes](#when-a-table-needs-more-indexes) for what happens above it. |
| `max-index-columns`     | **integer** | `3`     | The most columns of one index. PostgreSQL hash indexes always have one column.                                                                                      |
| `max-filter-patterns`   | **integer** | `50`    | The most distinct filter patterns on one table. Above it, the compiler creates a single-column index for each filtered column instead of composite indexes, and warns. |
| `min-cost-reduction`    | **number**  | `0.05`  | How much an index must at least cut the cost of the queries it serves, as a fraction: `0.05` is 5%. Must be at least `0` and less than `1`.                         |
| `small-table-row-limit` | **integer** | `100`   | A table that holds at most this many rows, by its definition or a `row_count` hint, gets no automatic index. `0` turns this off.                                    |
| `min-distinct-count`    | **integer** | `20`    | An equality column gets no place in an index when a `row_count` hint gives it fewer distinct values than this, or shows that it multiplies the distinct values of the other equality columns by less than this. `0` turns this off. |

An `index` hint on a table replaces the automatic selection for that table, so these limits do not apply to it.

```json
{
  "engines": {
    "postgres": {
      "index-selection": {
        "max-indexes": 12,
        "small-table-row-limit": 0
      }
    }
  }
}
```

The keys that you leave out keep their defaults.

### When a table needs more indexes

The compiler first selects the indexes that the filter patterns of a table need, without a limit. When they are more than `max-indexes`, it does one of two things and warns:

- When one index for each filtered column gives fewer indexes, it creates those single-column indexes and none of the selected ones. PostgreSQL combines single-column indexes at query time. A column gets a hash index when the queries only compare it by `=`, and a btree index otherwise. In this scenario, the result can have more indexes than `max-indexes`.
- Otherwise it creates the `max-indexes` indexes that cut the query cost the most. The warning lists the indexes that the limit omits, in the form of the `index` hint, and the filter patterns that are left with a full table scan:

```text
Created the maximum of 8 indexes for table `Orders_1`. Its query filter patterns need 9 indexes.
The limit omits these indexes: index(HASH, currency). These query filter patterns have no supporting index and require a full table scan: (currency). 
The query results are not affected.
See the indexes of the table in `pipeline_explain.txt`. To select different indexes, either specify them explicitly with an `index` hint or reduce the number of distinct filter patterns on this table.
```

A table with more than `max-filter-patterns` filter patterns gets the single-column indexes directly, with a warning.

These warnings are about query speed only. The queries return the same rows with any set of indexes. [`pipeline_explain.txt`](../compilation-output) lists the indexes that the compiler created for each table.

## Conflict Handling

When a generated PostgreSQL table receives a row that conflicts with an existing row on a primary key or unique constraint,
DataSQRL chooses one of the following conflict handling strategies:

| Strategy         | PostgreSQL behavior                                                                 | Description                                                                                                                                                                                                                      |
|------------------|-------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Update           | `ON CONFLICT (...) DO UPDATE SET ...`                                               | The existing row is overwritten with the incoming row.                                                                                                                                                                           |
| Timestamp update | `ON CONFLICT (...) DO UPDATE SET ... WHERE incoming timestamp >= existing timestamp` | The existing row is overwritten only when the incoming timestamp is not older than the existing one. Otherwise, the conflicting insert is silently skipped, which prevents out-of-order events from rolling back newer state. |
| Ignore           | `ON CONFLICT (...) DO NOTHING`                                                      | The existing row is kept, and the conflicting insert is silently skipped.                                                                                                                                                        |

DataSQRL applies these strategies automatically based on the generated [table type](../sqrl-language#type-system):

- `STATE` tables use timestamp update with the appropriate timestamp column.
- `STREAM` tables use ignore.
- Other PostgreSQL tables use update.

To override the automatic choice, set `sink.on-conflict.action` to `UPDATE`, `TIMESTAMP`, or `IGNORE` in the `postgres` [connector template](../configuration#connector-templates-connectors).
The template applies to every PostgreSQL table, and `TIMESTAMP` also requires `sink.on-conflict.timestamp-column` to name a timestamp column that exists in each table.

The primary key of a `STREAM` table is expected to identify each row, and a `STREAM` table without a primary key is keyed on a hash of all its columns.
DataSQRL does not enforce this. When it holds, a conflict is a replay of a row that was already written, for example after the pipeline restarts from a checkpoint, and every strategy stores the same row.
When rows with the same key differ, those in one write batch are first reduced to the last one, and the strategy then decides between that row and the stored one. Ignore keeps the stored row.

## Usage Notes

- Database schema is automatically generated from your SQRL script
- Tables, indexes, and views are created based on the compiled data pipeline
- Connection parameters are typically provided via environment variables
- The engine handles both real-time data ingestion and query serving
- Optimized for low-latency reads of materialized data
- Read replicas improve query performance and provide redundancy
